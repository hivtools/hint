## Differences from Kotlin

The goldens in `contract-tests/goldens` are recorded from the Kotlin app only (`scripts/dev.sh up --no-proxy`, then `test --record`). Replaying them through the proxy shows where Python answers differently. These are written down for now and are to be reviewed together once everything is ported. Each is either to be matched in Python, or accepted and the golden re-recorded as a deliberate quirk. A scenario stops at its first difference, so there may be more behind the ones listed.

- **D1. 401 for a guest or anonymous caller.** Python answers `{"status":"failure","errors":[{"error":"OTHER_ERROR","detail":"Login required"}]}`. Kotlin (pac4j) answers a JSON body with `error: Unauthorized`, `path` and `timestamp` plus a `www-authenticate: Bearer realm="pac4j"` header, or an empty body for `/projects/`. `OPTIONS /project` is 405 with `Allow: POST` in Python, 401 in Kotlin. Tests: `pages_and_session/test_guest_gets_401_on_secured_prefixes`, `test_guest_projects_list_is_401_without_body`, `projects/test_create_project_as_guest_is_401`, `misc_edges/test_head_and_options_requests`, and the "still a guest" steps in `auth/test_login_wrong_password`, `auth/test_logout_destroys_session_and_redirects_to_login`, `sso/test_sso_idp_failures`, `sso/test_sso_logout_redirects_to_idp`.
- **D2. `Accept-Language` negotiation.** Python maps `pt-BR` to Portuguese and `fr;q=0.5` to French. Kotlin answers English for both. Tests: `misc_edges/test_accept_language_variants_for_hint_errors[pt-BR]` and `[q-value]`.
- **D3. Text of the "unexpected error" message.** The user-facing part is the same. Kotlin appends the Spring or Jackson reason (for example `Required request body is missing: public org.springframework...`), Python only logs the reason. Tests: the `*_errors` and "no body" / "missing ..." steps in `projects/` and `versions/`, `baseline_files/test_upload_request_errors` ("wrong part name") and `session_files/test_set_files_malformed_requests` ("no body").
- **D4. No version in the session.** Python takes the version from `X-Version-Id` and keeps nothing in the Kotlin session. Deleting a project from a session with no current project succeeds (Kotlin: 400). After a failed new version the session still points at a version that exists, so the next upload works (Kotlin: 500). `/project/current` without the header is `null` (Kotlin: the session's version). Tests: `projects/test_delete_project_fails_with_400_when_session_has_no_current_project_but_still_deletes`, `versions/test_failed_new_version_leaves_session_pointing_at_a_nonexistent_version`, `version_header/test_without_the_header_the_version_in_the_session_is_used`, and for the files, `baseline_files/test_upload_before_opening_app_fails_because_version_row_missing` (403 `INVALID_VERSION`, Kotlin: 500), `session_files/test_set_files_before_opening_app` and `test_set_files_guest_session`, `auth/test_guest_session_files_survive_login`, and `pages_and_session/test_json_responses_are_gzipped_when_accepted`, `test_sessions_are_isolated_between_clients` and `test_session_persists_across_requests` (these send no `X-Version-Id` with their uploads, so they only work with the Kotlin session).
- **D5. hintr failures (the passthrough endpoints).** (a) A body that is not JSON, such as the HTML 502 or 504 page of a gateway, gives `Could not parse response.` (500). Kotlin gives ADR wording, `Failed to get response from ADR, try again later.` (502) or `ADR request timed out` (504), because hintr and ADR answers share one converter there. (b) A JSON error with no `status` field gives the JSON text as the message. Kotlin gives an empty message. (c) Python calls hintr once when the connection is dropped, Kotlin twice. Tests: `hintr_faults/test_hintr_non_json_error_bodies`, `test_hintr_connection_dropped`, `test_hintr_down_for_each_validation_endpoint`, `model/test_status_result_of_unknown_ids`.
- **D6. Requests with a body that is not valid, and wrong methods.** For a POST that takes a JSON body, a body that is missing or has the wrong fields is 400 in both. A field of the wrong type is 400 in Python where Kotlin gives 500 (`meta/review-inputs` with `types` as a string). A wrong method, such as GET on a POST only path, is 405 `Method Not Allowed` with an `Allow` header in Python, where Kotlin gives its "unexpected error" text and no `Allow`. Tests: `chart_data/test_review_inputs_metadata_errors` ("types not a list"), `model/test_validate_options_bad_requests` ("wrong method"). The upload endpoints: a request with no body, or with JSON, where there should be a file is 400 (Kotlin: 500), and the file as a plain form field is 415 (Kotlin: 500); the same for `/session/files` with a form body, which is 415 in both (`baseline_files/test_upload_request_errors`).
- **D7. Endpoints that read the results folder.** (a) When hintr cannot give the path of a result (an unknown task id, or one that is not a finished calibration or download), Python answers hintr's own failure (400, as it does for the passthrough endpoints). Kotlin's `filteredData` answers 500 "unexpected error", because it reads the path out of a failure. (b) `download/result`: Python makes one call to hintr, `GET /download/result/path/{id}`, and sends the file from the results folder in pieces. Kotlin makes a `HEAD` and a `GET /download/result/{id}`, and hintr reads the whole file into memory. The content type (`application/octet-stream`) and the `Content-Disposition` (`attachment; filename="<areas>_<label>_<yyyymmdd-hhmm><ext>"`, the time made in Python in UTC) are the same. Python's answer also has `Content-Length`, `ETag`, `Last-Modified` and supports range requests. A `HEAD` to hint is 405 (Kotlin answers it as a `GET`), the Vue app only uses `GET`. (c) A result file that hintr names but is not in the results folder: `filteredData` is 400 `missingCalibrateData`, as in Kotlin. `download/result` is 500 "unexpected error" with the path in the log. The contract tests do not cover either. Tests: `calibrate/test_filtered_data_bad_requests` ("unknown id", "failed calibration id"), and the outbound calls of the "result" steps in `downloads/test_status_and_result_of_each_type[*]`, `test_download_result_and_metadata_errors` and `test_download_as_guest`. The rows of `filteredData` are the same as Kotlin's, byte for byte on the Malawi mock fit (the numbers are sent at 32 bit precision, as Kotlin did).
- **D8. No response compression (held off for now).** Kotlin compresses JSON responses of 1 KB or more (`server.compression.*` in `application.properties`, applied when the browser sends `Accept-Encoding: gzip`). The Python API and the nginx proxy compress nothing, so every large JSON answer is sent whole. Measured on the Malawi mock calibration with `filteredData`: 20,493 rows are 0.57 MB on the wire from Kotlin and 4.31 MB from Python, and all 350,244 rows are 10.0 MB and 73.0 MB. Python is still about 2 to 3 times faster to answer (106 ms against 234 to 299 ms, and 1.1 s against 3.6 to 4.3 s), but on a slow connection the bytes matter more than that. It affects every Python endpoint with a big body (the chart data, the review inputs metadata, the model and calibrate results, as well as `filteredData`). This is R11, step 3 in [target-design.md](target-design.md). Not done yet. Open: where to compress. nginx is the cheaper place (compiled, and level 1 to 4 is fast), whereas Starlette's `GZipMiddleware` defaults to level 9, which is slow on 70 MB. Either way it must skip the file downloads, which are already compressed.
- **D9. Files that are uploaded and set.** (a) A file that is in the `file` table but not on the disk is written again when the same content is uploaded (Kotlin only writes a file when its hash is new, so it stays missing, `file_storage/test_file_row_present_but_file_missing_on_disk`). Python hashes the upload first, and does not write it to the share if a file of that name and size is there already, as Kotlin did not. A file that is not there (or is the wrong size, as a Kotlin write that stopped half way leaves it) is written to a temporary name in the same folder, which is then renamed, and the hash is recorded after (design rule R2). (b) `POST /session/files` with a type that is not one of the file types (`anc`, `pjnz`, `population`, `programme`, `shape`, `survey`, `vmmc`) is 400. Kotlin stores it, and nothing ever reads it (`session_files/test_set_files_accepts_arbitrary_type_keys`). (c) A hash that no upload made is 400 `loadFailed`, as in Kotlin, but Python looks for it before it changes anything instead of relying on the foreign key. Any hash that has been uploaded by anyone is still accepted (quirk 22, kept). (d) The extension of a stored file is the text after the last dot of the last part of the file name. For names a browser sends this is the same as Kotlin. A name with directories in it (`../../x`) made Kotlin write outside of its folder, and Python keeps to the folder (`misc_edges/test_filename_with_path_components`: a name with directories is kept as it is, for hintr and the database, as in Kotlin). A name that starts with a Windows drive or share (`C:\\Users\\me\\a.PJNZ`) is cut to its last part by the multipart parser before this API sees it, where Kotlin kept all of it. Browsers send only the name. (e) A file replaces the version's file of that type as in Kotlin: Python updates the row if there is one and inserts a row if not. Two uploads at once of a file type that the version has no file for yet can both insert, as in Kotlin (see [Deferred](#deferred-until-kotlin-is-gone)). (g) A `vmmc` entry in `POST /session/files` is ignored: Kotlin stores it. Nothing uses VMMC files now, but the front end sends back the files of an old saved version, which can include one. The version does not get the file, its hash is not checked and the response does not have it (`test_input_files.py::test_the_vmmc_file_of_an_old_project_is_ignored`). (f) **Kept, not fixed**: a file that hintr rejects (or whose shape or PJNZ file is missing) still replaces the one the version had (quirks 6 and 9, `*/test_failed_validation_still_replaces_*`). QUIRKS.md proposes to keep the old file, but the Vue app takes the file off the screen as soon as an upload starts, so keeping it on the server would leave the screen and the server disagreeing. It needs a change in the front end as well. (h) **New**: an upload is refused with 413 and the error `FILE_TOO_LARGE` when the request is bigger than the limit for its kind of file. Kotlin had no limit. The limits are about twice the largest file of the kind that a saved version used in November 2026: PJNZ 400 MB (largest 187 MB, a subnational projection that may be a zip), population 150 MB (67 MB), shape 100 MB (44 MB), survey 50 MB (25 MB), programme 20 MB (8 MB) and ANC 10 MB (under 1 MB). Each has a setting, such as `HINT_MAX_PJNZ_UPLOAD_BYTES`. Subnational PJNZ files may grow, so check again if a refusal is reported. The check is made as the request arrives (`app/upload_limit.py`), by Content-Length and by counting, so a large file is not received or stored. Each upload in flight takes its size of the replica's ephemeral disk while it is received (4 GiB at 1 vCPU on Container Apps, so about 10 uploads of the largest PJNZ fit at once, see the note in `upload_limit.py`). (i) **The `.zip` limit**: an uploaded PJNZ may be a `.zip`, so it is within the 400 MB limit of (h) (the largest real PJNZ was 187 MB). Output zips are a different case. The largest output zip a saved version used was 234 MB (38 of them are used), and the largest `.zip` in the share was 481 MB (no version uses it), and the limits of (h) is not meant for them: `/rehydrate/zip` (not ported yet) needs a limit of its own, set when it is ported. Tests: `file_storage/test_file_row_present_but_file_missing_on_disk`, `session_files/test_set_files_accepts_arbitrary_type_keys`, `misc_edges/test_filename_with_path_components`. The goldens that stop at their first difference (D3, D4 and D6 above) hide later steps, which `hint-py/tests/api/test_input_files.py` checks instead.
- **D10. No `strict` parameter, and no PJNZ gate.** Kotlin reads `?strict=` on `/disease/{survey,programme,anc,vmmc}` (and `/adr/*`): only the exact text `false` turns it off. In strict mode (the default) it refuses the upload with 400 `missingPjnzFile` when the version has no PJNZ file ([HintrController.kt](../src/app/src/main/kotlin/org/imperial/mrc/hint/controllers/HintrController.kt) `validate`), as well as with `missingShapeFile` when it has no shape file. It also sends `?strict=true` or `false` on to hintr on `/validate/survey-and-programme`. hintr has not used `strict` since its strict ANC check was removed (hintr `ae07f7f6`, 1.2.11), the request to hintr has only the file and the shape file (never the PJNZ file), and `strict` is being removed from hintr (hintr PR 574, which refuses an unknown query parameter). So the PJNZ check is only a gate in hint. The Vue app does not enforce it either (the survey, programme and ANC boxes are never disabled without a PJNZ file), so a user only saw the error after an upload, and the rejected file was kept (quirk 6). The Vue app is changed to stop sending `strict` (it always sent `true`). **Python has no `strict` parameter and no PJNZ gate**: it ignores `?strict=`, needs only the shape file (400 `missingShapeFile` without it), validates the file with hintr, and calls hintr with no query. `MissingPjnzFileError` and the `missingPjnzFile` message are removed. The recorded goldens differ in three ways: the outbound hintr calls have `query: strict=true` (or `false`); a survey, programme or ANC upload or get with a shape file but no PJNZ file is validated by Python where Kotlin answers 400 `missingPjnzFile` (`disease_files/test_missing_shape_and_pjnz[*]`, `disease_files/test_strict_parameter_semantics`, `chart_data/test_input_time_series_needs_shape_and_pjnz`, `model/test_model_options_missing_files`, `adr_import/test_import_needs_shape_for_disease_files` and others; not all checked); and where Kotlin asks for the PJNZ file first (no shape and no PJNZ) Python asks for the shape file. The contract tests need `strict` taken out and the goldens re-recorded against Kotlin once Kotlin stops sending it and has no PJNZ gate. Tests: `hint-py/tests/api/test_input_files.py::test_without_a_pjnz_file_an_upload_is_validated`, `::test_the_strict_query_parameter_is_ignored`.

## Deferred until Kotlin is gone

Changes that need the database to change. Kotlin shares the database, so they wait until Kotlin no longer runs against it.

- **Z1. One file per type for a version, enforced by the database.** The primary key of `version_file` is `(version, hash, type)`, so nothing stops a version having two rows of one type with different hashes. Today the code keeps to one row per type (D9 (e)). Two uploads at once of a type the version has no file for yet can both insert: with the same file the second fails on the primary key (a 500), and with different files the version gets two rows of that type, and `GET /session/files` shows one of them. Kotlin has the same race, and a lock would only order Python against Python, so Python does not take one. To fix it: (1) find and remove duplicate `(version, type)` rows that exist already (the migration fails if there are any), (2) add `UNIQUE (version, type)`, (3) replace the select and update or insert in `VersionRepository.save_version_file` with one `insert ... on conflict (version, type) do update`, and (4) add a test with concurrent uploads to a version with no file (it needs Postgres, as SQLite does not run the requests at the same time). `set_files_for_version` (delete all, then insert) can use the same constraint.
