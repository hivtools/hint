# Python port checklist

Every endpoint of the Kotlin app, in the order of the [endpoint index](endpoint-flows.md#endpoint-index). **nginx sends everything to Python now ([D23](#differences-from-kotlin)): what is not ticked answers 404.** Tick `[ ]` to `[x]` in the Ported column when the endpoint is served by Python (a `location` in [proxy/nginx.conf.template](../proxy/nginx.conf.template)) and the regression suite passes through the proxy, or the differences are written down in the Notes column and in [Differences from Kotlin](#differences-from-kotlin). See [proxy/README.md](../proxy/README.md).

100 rows: 98 endpoints of Kotlin (two, `POST /guest/version` and `/internal/whoami`, were added to the list late), and `/me` and `POST /dev-login`, which are new in Python. Flows, hintr calls and Redis use for each are in [endpoint-flows.md](endpoint-flows.md).

## Differences from Kotlin

The goldens in `contract-tests/goldens` are recorded from the Kotlin app only (`scripts/dev.sh up --no-proxy`, then `test --record`). Replaying them through the proxy shows where Python answers differently. These are written down for now and are to be reviewed together once everything is ported. Each is either to be matched in Python, or accepted and the golden re-recorded as a deliberate quirk. A scenario stops at its first difference, so there may be more behind the ones listed.

- **D1. 401 for a guest or anonymous caller.** Python answers `{"status":"failure","errors":[{"error":"OTHER_ERROR","detail":"Login required"}]}`. Kotlin (pac4j) answers a JSON body with `error: Unauthorized`, `path` and `timestamp` plus a `www-authenticate: Bearer realm="pac4j"` header, or an empty body for `/projects/`. `OPTIONS /project` is 405 with `Allow: POST` in Python, 401 in Kotlin. Tests: `pages_and_session/test_guest_gets_401_on_secured_prefixes`, `test_guest_projects_list_is_401_without_body`, `projects/test_create_project_as_guest_is_401`, `misc_edges/test_head_and_options_requests`, and the "still a guest" steps in `auth/test_login_wrong_password`, `auth/test_logout_destroys_session_and_redirects_to_login`, `sso/test_sso_idp_failures`, `sso/test_sso_logout_redirects_to_idp`, and for the four ADR endpoints `adr_browse/test_adr_endpoints_guest_401`.
- **D2. `Accept-Language` negotiation.** Python maps `pt-BR` to Portuguese and `fr;q=0.5` to French. Kotlin answers English for both. Tests: `misc_edges/test_accept_language_variants_for_hint_errors[pt-BR]` and `[q-value]`.
- **D3. Text of the "unexpected error" message.** The user-facing part is the same. Kotlin appends the Spring or Jackson reason (for example `Required request body is missing: public org.springframework...`), Python only logs the reason. Tests: the `*_errors` and "no body" / "missing ..." steps in `projects/` and `versions/`, `baseline_files/test_upload_request_errors` ("wrong part name") and `session_files/test_set_files_malformed_requests` ("no body"). Also the ADR endpoints with a parameter that is missing or wrong: `adr_browse/test_datasets_bad_requests` ("no type"), `test_datasets_show_inaccessible_flag` ("showInaccessible=maybe") and `test_orgs` ("permission missing").
- **D4. No version in the session.** Python takes the version from `X-Version-Id` and keeps nothing in the Kotlin session. Deleting a project from a session with no current project succeeds (Kotlin: 400). After a failed new version the session still points at a version that exists, so the next upload works (Kotlin: 500). `/project/current` without the header is `null` (Kotlin: the session's version). Tests: `projects/test_delete_project_fails_with_400_when_session_has_no_current_project_but_still_deletes`, `versions/test_failed_new_version_leaves_session_pointing_at_a_nonexistent_version`, `version_header/test_without_the_header_the_version_in_the_session_is_used`, and for the files, `baseline_files/test_upload_before_opening_app_fails_because_version_row_missing` (403 `INVALID_VERSION`, Kotlin: 500), `session_files/test_set_files_before_opening_app` and `test_set_files_guest_session`, `auth/test_guest_session_files_survive_login`, and `pages_and_session/test_json_responses_are_gzipped_when_accepted`, `test_sessions_are_isolated_between_clients` and `test_session_persists_across_requests` (these send no `X-Version-Id` with their uploads, so they only work with the Kotlin session).
- **D5. hintr failures (the passthrough endpoints).** (a) A body that is not JSON, such as the HTML 502 or 504 page of a gateway, gives `Could not parse response.` (500). Kotlin gives ADR wording, `Failed to get response from ADR, try again later.` (502) or `ADR request timed out` (504), because hintr and ADR answers share one converter there. (b) A JSON error with no `status` field gives the JSON text as the message. Kotlin gives an empty message. (c) Python calls hintr once when the connection is dropped, Kotlin twice. Tests: `hintr_faults/test_hintr_non_json_error_bodies`, `test_hintr_connection_dropped`, `test_hintr_down_for_each_validation_endpoint`, `model/test_status_result_of_unknown_ids`.
- **D6. Requests with a body that is not valid, and wrong methods.** For a POST that takes a JSON body, a body that is missing or has the wrong fields is 400 in both. A field of the wrong type is 400 in Python where Kotlin gives 500 (`meta/review-inputs` with `types` as a string). A wrong method, such as GET on a POST only path, is 405 `Method Not Allowed` with an `Allow` header in Python, where Kotlin gives its "unexpected error" text and no `Allow`. Tests: `chart_data/test_review_inputs_metadata_errors` ("types not a list"), `model/test_validate_options_bad_requests` ("wrong method"). The upload endpoints: a request with no body, or with JSON, where there should be a file is 400 (Kotlin: 500), and the file as a plain form field is 415 (Kotlin: 500); the same for `/session/files` with a form body, which is 415 in both (`baseline_files/test_upload_request_errors`).
- **D7. Endpoints that read the results folder.** (a) When hintr cannot give the path of a result (an unknown task id, or one that is not a finished calibration or download), Python answers hintr's own failure (400, as it does for the passthrough endpoints). Kotlin's `filteredData` answers 500 "unexpected error", because it reads the path out of a failure. (b) `download/result`: Python makes one call to hintr, `GET /download/result/path/{id}`, and sends the file from the results folder in pieces. Kotlin makes a `HEAD` and a `GET /download/result/{id}`, and hintr reads the whole file into memory. The content type (`application/octet-stream`) and the `Content-Disposition` (`attachment; filename="<areas>_<label>_<yyyymmdd-hhmm><ext>"`, the time made in Python in UTC) are the same. Python's answer also has `Content-Length`, `ETag`, `Last-Modified` and supports range requests. A `HEAD` to hint is 405 (Kotlin answers it as a `GET`), the Vue app only uses `GET`. (c) A result file that hintr names but is not in the results folder: `filteredData` is 400 `missingCalibrateData`, as in Kotlin. `download/result` is 500 "unexpected error" with the path in the log. The contract tests do not cover either. Tests: `calibrate/test_filtered_data_bad_requests` ("unknown id", "failed calibration id"), and the outbound calls of the "result" steps in `downloads/test_status_and_result_of_each_type[*]`, `test_download_result_and_metadata_errors` and `test_download_as_guest`. The rows of `filteredData` are the same as Kotlin's, byte for byte on the Malawi mock fit (the numbers are sent at 32 bit precision, as Kotlin did).
- **D8. No response compression (held off for now).** Kotlin compresses JSON responses of 1 KB or more (`server.compression.*` in `application.properties`, applied when the browser sends `Accept-Encoding: gzip`). The Python API and the nginx proxy compress nothing, so every large JSON answer is sent whole. Measured on the Malawi mock calibration with `filteredData`: 20,493 rows are 0.57 MB on the wire from Kotlin and 4.31 MB from Python, and all 350,244 rows are 10.0 MB and 73.0 MB. Python is still about 2 to 3 times faster to answer (106 ms against 234 to 299 ms, and 1.1 s against 3.6 to 4.3 s), but on a slow connection the bytes matter more than that. It affects every Python endpoint with a big body (the chart data, the review inputs metadata, the model and calibrate results, as well as `filteredData`). This is R11, step 3 in [target-design.md](target-design.md). Not done yet. Open: where to compress. nginx is the cheaper place (compiled, and level 1 to 4 is fast), whereas Starlette's `GZipMiddleware` defaults to level 9, which is slow on 70 MB. Either way it must skip the file downloads, which are already compressed.
- **D9. Files that are uploaded and set.** (a) A file that is in the `file` table but not on the disk is written again when the same content is uploaded (Kotlin only writes a file when its hash is new, so it stays missing, `file_storage/test_file_row_present_but_file_missing_on_disk`). Python hashes the upload first, and does not write it to the share if a file of that name and size is there already, as Kotlin did not. A file that is not there (or is the wrong size, as a Kotlin write that stopped half way leaves it) is written to a temporary name in the same folder, which is then renamed, and the hash is recorded after (design rule R2). (b) `POST /session/files` with a type that is not one of the file types (`anc`, `pjnz`, `population`, `programme`, `shape`, `survey`, `vmmc`) is 400. Kotlin stores it, and nothing ever reads it (`session_files/test_set_files_accepts_arbitrary_type_keys`). (c) A hash that no upload made is 400 `loadFailed`, as in Kotlin, but Python looks for it before it changes anything instead of relying on the foreign key. Any hash that has been uploaded by anyone is still accepted (quirk 22, kept). (d) The extension of a stored file is the text after the last dot of the last part of the file name. For names a browser sends this is the same as Kotlin. A name with directories in it (`../../x`) made Kotlin write outside of its folder, and Python keeps to the folder (`misc_edges/test_filename_with_path_components`: a name with directories is kept as it is, for hintr and the database, as in Kotlin). A name that starts with a Windows drive or share (`C:\\Users\\me\\a.PJNZ`) is cut to its last part by the multipart parser before this API sees it, where Kotlin kept all of it. Browsers send only the name. (e) A file replaces the version's file of that type as in Kotlin: Python updates the row if there is one and inserts a row if not. Two uploads at once of a file type that the version has no file for yet can both insert, as in Kotlin (see [Deferred](#deferred-until-kotlin-is-gone)). (g) A `vmmc` entry in `POST /session/files` is ignored: Kotlin stores it. Nothing uses VMMC files now, but the front end sends back the files of an old saved version, which can include one. The version does not get the file, its hash is not checked and the response does not have it (`test_input_files.py::test_the_vmmc_file_of_an_old_project_is_ignored`). (f) **Kept, not fixed**: a file that hintr rejects (or whose shape or PJNZ file is missing) still replaces the one the version had (quirks 6 and 9, `*/test_failed_validation_still_replaces_*`). QUIRKS.md proposes to keep the old file, but the Vue app takes the file off the screen as soon as an upload starts, so keeping it on the server would leave the screen and the server disagreeing. It needs a change in the front end as well. (h) **New**: an upload is refused with 413 and the error `FILE_TOO_LARGE` when the request is bigger than the limit for its kind of file. Kotlin had no limit. The limits are about twice the largest file of the kind that a saved version used in November 2026: PJNZ 400 MB (largest 187 MB, a subnational projection that may be a zip), population 150 MB (67 MB), shape 100 MB (44 MB), survey 50 MB (25 MB), programme 20 MB (8 MB) and ANC 10 MB (under 1 MB). They are in the code (`INPUT_FILE_TYPES` in `app/services/upload_file_types.py`), not in the settings. Subnational PJNZ files may grow, so check again if a refusal is reported. The check is made as the request arrives (`app/middleware/upload_limit.py`), by Content-Length and by counting, so a large file is not received or stored. Each upload in flight takes its size of the replica's ephemeral disk while it is received (4 GiB at 1 vCPU on Container Apps, so about 10 uploads of the largest PJNZ fit at once, see the note in `upload_limit.py`). (i) **New**: a file whose extension is not one that hintr accepts for the type is refused before anything is written: PJNZ takes `PJNZ` or `zip`, shape takes `geojson`, and population, survey, programme and ANC take `csv` (case does not matter). The answer is hint's own error in its usual shape (400, `INVALID_FILE_EXTENSION`, "File must be of type geojson, got type shp." in the language of the request) and hintr is not asked. Kotlin passed on hintr's answer, which has the code `INVALID_FILE` and a random `key` for support to find in hintr's log. Python's answer has neither, as hintr no longer takes part (the Vue app shows only the `detail`). Kotlin wrote every file to the share and attached it, then let hintr refuse it, so the share holds stray files (in November 2026 `.shp`, `.exe`, `.jpg` and `.docx` among others). Python also takes off the file that the version had of that type, as the Vue app has taken it off the screen (the kept quirks 6 and 9 show why a refused file should not stay on the server unseen). Kotlin kept the refused file attached, where a later `GET` showed the same error. (j) **The `.zip` limit**: an uploaded PJNZ may be a `.zip`, so it is within the 400 MB limit of (h) (the largest real PJNZ was 187 MB). Output zips are a different case. The largest output zip a saved version used was 234 MB (38 of them are used), and the largest `.zip` in the share was 481 MB (no version uses it), and the limits of (h) are not meant for them: `POST /rehydrate/zip` and `POST /rehydrate/adr` have a limit of their own, 500 MB, with the reasons in [D18](#differences-from-kotlin) (a). Tests: `file_storage/test_file_row_present_but_file_missing_on_disk`, `session_files/test_set_files_accepts_arbitrary_type_keys`, `misc_edges/test_filename_with_path_components`. The goldens that stop at their first difference (D3, D4 and D6 above) hide later steps, which `hint-py/tests/api/test_input_files.py` checks instead.
- **D10. No `strict` parameter, and no PJNZ gate.** Kotlin reads `?strict=` on `/disease/{survey,programme,anc,vmmc}` (and `/adr/*`): only the exact text `false` turns it off. In strict mode (the default) it refuses the upload with 400 `missingPjnzFile` when the version has no PJNZ file ([HintrController.kt](../src/app/src/main/kotlin/org/imperial/mrc/hint/controllers/HintrController.kt) `validate`), as well as with `missingShapeFile` when it has no shape file. It also sends `?strict=true` or `false` on to hintr on `/validate/survey-and-programme`. hintr has not used `strict` since its strict ANC check was removed (hintr `ae07f7f6`, 1.2.11), the request to hintr has only the file and the shape file (never the PJNZ file), and `strict` is being removed from hintr (hintr PR 574, which refuses an unknown query parameter). So the PJNZ check is only a gate in hint. The Vue app does not enforce it either (the survey, programme and ANC boxes are never disabled without a PJNZ file), so a user only saw the error after an upload, and the rejected file was kept (quirk 6). The Vue app is changed to stop sending `strict` (it always sent `true`). **Python has no `strict` parameter and no PJNZ gate**: it ignores `?strict=`, needs only the shape file (400 `missingShapeFile` without it), validates the file with hintr, and calls hintr with no query. `MissingPjnzFileError` and the `missingPjnzFile` message are removed. The recorded goldens differ in three ways: the outbound hintr calls have `query: strict=true` (or `false`); a survey, programme or ANC upload or get with a shape file but no PJNZ file is validated by Python where Kotlin answers 400 `missingPjnzFile` (`disease_files/test_missing_shape_and_pjnz[*]`, `disease_files/test_strict_parameter_semantics`, `chart_data/test_input_time_series_needs_shape_and_pjnz`, `model/test_model_options_missing_files`, `adr_import/test_import_needs_shape_for_disease_files` and others; not all checked); and where Kotlin asks for the PJNZ file first (no shape and no PJNZ) Python asks for the shape file. The contract tests need `strict` taken out and the goldens re-recorded against Kotlin once Kotlin stops sending it and has no PJNZ gate. Tests: `hint-py/tests/api/test_input_files.py::test_without_a_pjnz_file_an_upload_is_validated`, `::test_the_strict_query_parameter_is_ignored`.
- **D11. No password login, and no stored ADR key.** Password login is only used in local development, and every deployed login is Auth0 single sign-on. Python has no password form, no password reset (`/password/*`, SMTP, the `onetime_token` table), and no `/adr/key` (the stored, RSA encrypted API key and the key entry in the Vue app), and no `/sso` (the front end stops asking). **Dev login.** In local development the login page shows one button for each user in `HINT_DEV_USERS` (the dev stack has `test.user@example.com,naomi-support@imperial.ac.uk`, the users of the contract tests), then "Continue as guest", where deployed it shows the Auth0 button. A button posts to `POST /dev-login`, which creates the user if needed and a session in the same way as an Auth0 login, so that sharing and cloning between two users can be tried locally. The route is not registered unless `HINT_DEV_USERS` is set, and startup is refused if it is set with Auth0 settings or an `https` application URL. Logout in a dev session returns to the login page and skips Auth0. **ADR credential.** One function picks it: the Auth0 access token if the request has one (the identity bridge passes it on as `X-Hint-Access-Token` until login moves to Python), otherwise `HINT_ADR_API_KEY`, which is for development only. Guest mode and `/user/{email}/exists` stay. The front end no longer sends `/sso` or `/adr/key` and has no key entry (Kotlin is not routed any more, so they answer 404). **Done with login (D22):** the dev login (`POST /dev-login`, the buttons on the login page), `HINT_DEV_USERS` in `docker-compose.yml`, and Playwright logs in with it. The contract tests log in with it on a replay (D22 (j)). **Still to do:** `add-test-user.sh` and the `db-users` service still give users a password, which nothing uses. **Check before relying on it:** that no password users and no `ADR_key` rows in use exist in production. The ADR credential is done (see D12). Kotlin keeps its password login, unrouted except `/callback/formClient`, until it is removed.
- **D12. How ADR is called, and as whom.** (The login decision of D11 is the reason.) Kotlin keeps each user's ADR API key, encrypted, in the database (`ADR_key`) and calls ADR with it, or, for a single sign-on login, with the Auth0 access token of the session. Python has no stored key: it calls ADR as the user with the access token if the proxy passes one on (`X-Hint-Access-Token`), and otherwise with `HINT_ADR_API_KEY`, which is for development only. Both go to one address, `adr_url` (Kotlin has two, `adr_url` and `oauth2_client_adr_server_url`, which are the same in `src/docker/config.properties`, so a deployment only needs `HINT_ADR_URL`). The ADR stub is on the host, so in the dev stack the Python container gets `http://host.docker.internal:<port>/adr/` as `HINT_ADR_URL`, which the contract tests count as the same address as Kotlin's (`normalize.py`) (`scripts/dev.sh` sets it to the key of the ADR stub). It is development only for real: `HINT_ADR_API_KEY` needs `HINT_ENVIRONMENT=development`, and the API does not start with them in the default `production` (otherwise every user would be the same user on ADR). Without either the answer is 400 with the message `noADRKey`, now translated and saying to log in again (QUIRKS.md number 2, fixed: the message was the untranslated key). So a user who saved a key in the Kotlin app has it ignored by Python, which only matters outside single sign-on. Through the proxy the contract tests save a key with `POST /adr/key` (Kotlin), and Python uses `HINT_ADR_API_KEY` instead, which `scripts/dev.sh` sets to the same key, so the calls look alike. `adr_browse/test_datasets_without_stored_key` cannot pass through the proxy now (Python has the key from its settings, not from what the test stored). The ADR stub now listens on all addresses in the proxy mode of `dev.sh`, as the recording proxy of hintr does, so that the Python container reaches it. Tests: `hint-py/tests/api/test_adr_browse.py` (the credentials), `tests/clients/test_adr_client.py`.
- **D13. The calls to ADR, and their errors.** (a) A dropped connection to ADR: Python calls ADR once, Kotlin twice, as for hintr in D5 (c) (`adr_browse/test_datasets_adr_failures` "adr connection dropped", `test_dataset_show_adr_failures` "adr dropped connection"). (b) The parameters (the dataset id, the release, the permission) are encoded when Python calls ADR: Kotlin pastes them into the URL, so an id that has `&` or `#` in it could add or cut off parameters of the call. (c) Only the exact paths are Python's (`location =` and regular expressions in [nginx.conf.template](../proxy/nginx.conf.template)). The same paths with a trailing slash stay with Kotlin, and the Vue app now calls `/adr/datasets/{id}/releases` without one (`adr.ts`). `/adr/datasets/{id}/releases` is Python's for every method, and the push path `/adr/datasets/{id}/resource/{type}/{downloadId}` is a regular expression of its own (D19). (d) ADR's messages are not logged by Python (only the status, as in D3 and the README's "Personal data"). Kotlin logged them. (e) The French message for a failure to fetch the datasets has its apostrophes in Python: Kotlin passes it through `MessageFormat`, which reads a single quote as the start of quoted text (not covered by the contract tests). (f) The `type` of `/adr/datasets` is a choice of two values, so a value that is not one of them is the usual 400 "unexpected error" of D6. Kotlin gives 500. (g) The messages "No response returned. The request may have timed out.", "Could not parse response.", "ADR request timed out" and "Failed to get response from ADR, try again later." are translated (French, Portuguese) for the ADR endpoints and for the hintr endpoints. Kotlin shows them in English only, and the Vue app shows them to the user. The French and Portuguese texts are new and need a check by a translator. Tests: `adr_browse/test_datasets_adr_failures`, `test_dataset_show_adr_failures`, `test_releases_adr_failures` and the API tests in `hint-py/tests/api/test_adr_browse.py`. The ADR failures that the goldens do not reach (a scenario stops at its first difference) are in `test_adr_browse.py`, and `make test-adr` runs the endpoints against the real dev ADR (they need `ADR_TEST_KEY` and an IP address that the dev ADR lets in, so they fail on CI).
- **D14. Who owns the project or version is checked before the body.** The project endpoints that name a project or version in their path check that it is the user's before the endpoint runs (`owned_project` and `owned_version` in `hint-py/app/dependencies.py`), and FastAPI runs these before it checks the request body. Kotlin read the body first and then checked in the repository. So when the project or version is not the user's (or does not exist) and the body is wrong too, Python answers 400 `projectDoesNotExist` or `versionDoesNotExist`, where Kotlin answers with the error about the body. This is: a body that is missing or has the wrong fields (Kotlin: the 400 "unexpected error" of D3 and D6) on `rename`, `note` and `clone` of a project and `note` of a version; no body on `POST /project/{id}/version/{id}/state` (Kotlin: 400 "unexpected error"); and on `clone`, an email that is not valid or has no user (Kotlin: `invalidEmail` or `userDoesNotExist`, because it looked up the emails before the project). The status is 400 in every case, a request on the user's own project or version gets the same answer as in Kotlin, and the Vue app only sends valid bodies, so nothing the user sees changes. `POST /project/{id}/version` is not affected: the version it checks is in the body, so the body is checked first, as in Kotlin. The contract tests do not cover these. Tests: `hint-py/tests/api/test_projects.py::test_the_project_is_checked_before_the_body`, `test_versions.py::test_the_version_is_checked_before_the_body` and `::test_new_version_checks_the_body_before_the_parent`.
- **D15. Promote checks the version (quirk 30, fixed).** Kotlin's `promote` took the version id in the path and copied it into a new project without checking it: a user could copy another user's version, with its state and files, into a project of their own, and an id that does not exist gave a new project with an empty version (`versions/test_promote_does_not_check_version_or_ownership`). QUIRKS.md lists it under "Fix now". Python checks the version as the other version endpoints do (`VersionOfUser`): it must be in the project in the path, and the project must be the user's, or the answer is 400 `versionDoesNotExist` and nothing is created. The Vue app always sends the version's own project (`promoteVersion` in `store/projects/actions.ts`), so nothing the user sees changes. As for the endpoints of D14, the check comes before the body, so a body with no `name` on a version that is not the user's is `versionDoesNotExist` too (Kotlin: the 400 "unexpected error" of D3 and D6). The golden still records Kotlin, which has no check yet. Loading a project from an output zip (`POST /rehydrate/zip`, `POST /rehydrate/adr`).** The rules are in `app/services/rehydrate_service.py` (`RehydrateService.from_upload` and `from_adr`), and the safe reading of a zip is in `app/utils/zip_files.py`. (j) **The proxy.** `POST` of `/adr/datasets/{id}/releases` now goes to Python with the other methods (the `if ($request_method != GET) { return 418; }` fallback to Kotlin is gone, so PUT and DELETE of that path are Python's 405 where they were Kotlin's, checked through the proxy). The Vue app calls both paths without a trailing slash, and nothing in it changed. (k) **The contract replay** (`adr_push/*`, through the proxy on a second stack): nine scenarios pass as they are (releases with and without a same-name release, and the six input file types and the original file name). The others stop at known differences before they reach the push: the pipeline fixture of the output scenarios stops at the D10 `strict=true`, then at the hintr version, at VMMC (removed from Kotlin, PR 1144) and at the `agyw` download (D5 row of `/download/submit`). With a temporary copy of the contract tests that skips those four and notes every difference instead of stopping at the first one, all steps match the goldens except these. Known: the missing parameter text (D3: `name missing`, `resourceName missing`, `resourceFileName missing`, each in two or three scenarios), "no key" for a release (D12: Python has the key of its settings), the guest (D1), and `test_push_input_file[vmmc]` (Kotlin no longer has VMMC, D17 (h)). New: (c) the calls to hintr for the file (`GET /download/result/path/{id}` for `HEAD` and `GET /download/result/{id}`), and (d) hintr's failure as the answer in "unknown download id" and "id of a model fit". Tests: `hint-py/tests/api/test_adr_push.py` (every step above, in the order of the steps, with the fake ADR of `tests/adr.py` that keeps releases and resources and records the form and the file of each call), the write calls in `tests/clients/test_adr_client.py`, and `tests/api/test_adr_live_write.py`, which writes to the real dev ADR and is skipped unless `ADR_TEST_KEY` and `HINT_ADR_TEST_WRITE_DATASET` (a scratch dataset) are both set. Nothing sets them, and it was not run. (l) **The resource types on ADR are in the code, not in settings** (`INPUT_FILE_TYPES` and `OUTPUT_FILE_TYPES` in `app/services/file_types.py`, with the other facts about each kind of file). Kotlin read them from its bundled `config.properties`, which no deployment overrides, and they have not changed since August 2020; the dev ADR and the real one use the same ones. So there are no `HINT_ADR_*_SCHEMA` settings, only `HINT_ADR_URL` and the dataset types of this year and last year.

- **D20. Error reports (`POST /error-report`).** The endpoint is in `app/routers/error_report.py`. Where the report goes is behind `IssueReporter` (`app/clients/issue_reporter.py`), so that the Teams flow can be replaced (by Freshdesk or another helpdesk) without changing the endpoint. `TeamsFlowReporter` sends what Kotlin sent: the same JSON, with the same fields, to the same address. The contract replay matches the outbound call in every scenario. As in Kotlin, the report is sent first. If it was taken and names a project, the support user (`support_email`) gets a copy. The support user is looked up first (`userDoesNotExist`), then the project must be the logged in user's (`projectDoesNotExist`, and always for a guest). Whether the reporter is the support user is decided by the email in the body. The differences: (a) The flow's answer is read as hintr's is (`HintResponse.from_service`, now shared by both), so a JSON failure with no `status` has its JSON text as the message, where Kotlin's was empty (as D5 (b), `error_report/test_report_when_notification_fails` "flow answers 500"). The other failures of the flow (text, HTML, garbage with 200, no connection) give Kotlin's answers, which the Python tests check because the scenario stops at the first difference. (b) **New:** a success with no body (what a Power Automate flow with no Response action answers, 202) is a success with `data: null`. The goldens do not have this case. (c) `HINT_ISSUE_REPORT_URL` is a secret, because the key of the flow is in its `sig` parameter. `sig` is redacted from the httpx log line and from the traces, as `jwt` is. If it is not set, a report is an unexpected error (500). (d) A body that is not valid is 400 with the plain "unexpected error" text (D3), and GET is 405 (D6). **When the provider changes:** add a class with `send(report) -> HintResponse` and return it from `get_issue_reporter`. The outbound call in the goldens is the Teams JSON, so `contract-tests/tests/test_error_report.py` and its goldens will need to change with it.
- **D21. The page of the app, its files, and `GET /me`.** Python sends the page (`app/routers/pages.py`), and the page is the built `index.html`, a static file. (a) It has no user and no title in it: Kotlin's `index.ftl` had `var currentUser`, `data-user` and `data-title`, and the `<title>` of `application_title`. The Vue app now asks `GET /me` (new, `app/routers/me.py`) before it starts, and shows "Naomi could not start" if that fails, rather than taking the visitor to be a guest. The page's `<title>` is "Naomi" until the app sets the title from `/me`. (b) `GET /` no longer creates the session's version row (Kotlin's `HomeController.index` did, for the session fallback). Nothing needs it: each tab sends `X-Version-Id`, a guest tab gets its version from `POST /guest/version`, and the Python endpoints have no session fallback. (c) The page is `Cache-Control: no-cache` with an ETag, and answers HEAD. Kotlin sent no cache header for it. (d) A missing `/public/` file is a 404 (Kotlin: 500, quirk `test_missing_static_asset_is_500_not_404`). (e) Python gzips its answers of 1 KB or more (Starlette's `GZipMiddleware`, level 6) except `application/octet-stream` (the downloads) and what is compressed already. Kotlin (Spring Boot) gzipped a list of text types of 1 KB or more. Before this change Python gzipped nothing, so the JSON of the ported endpoints was not compressed through the proxy. (f) The page and `/public/` need no identity, so nginx does not ask Kotlin for these (`snippets/python-public.conf`), and the first visit gets no session cookie from `GET /`: it gets one from Kotlin when it first needs one (`POST /guest/version`, or login). Tests (26 scenarios differ only because of this, checked against a run of the same goldens before the change): (a) the scenarios that look for the user in the HTML: `pages_and_session/test_app_pages_guest` and `test_app_pages_logged_in`, `auth/test_second_login_replaces_first_user_in_same_session`, and the three `sso/test_sso_login_*`; (b) the `db:project_version` snapshots, which have one row fewer for each page that was opened: `projects/test_create_project_full`, `test_list_projects_hides_deleted_versions_and_projects`, `test_delete_project_is_soft`, `test_clone_project_to_another_user`, `test_clone_includes_soft_deleted_versions`, `test_clone_copies_files_and_state`, `versions/test_new_version_copies_files_and_state`, `test_save_and_load_state`, `test_update_version_note`, `test_promote_version_creates_a_new_project`, `version_header/test_a_guest_tab_is_given_its_own_version`, `error_report/test_report_with_project_clones_it_to_support_user`; (d) `pages_and_session/test_missing_static_asset_is_500_not_404`, and `test_static_assets` (the favicon is `image/vnd.microsoft.icon`, the registered type, where Kotlin said `image/x-icon`; browsers take both). The login page is still Kotlin until login moves (step 4).
- **D22. Login and sessions (`app/routers/login.py`, `app/services/web_sessions.py`, `app/routers/users.py`).** Python logs users in and keeps the sessions in Postgres (tables `web_session` and `web_session_guest_version`, hivtools/hint-db#26), as target design R6 says. nginx no longer asks Kotlin who the user is (no `/_whoami`, no `X-Hint-*` headers). (a) **The cookie** is `hint_session` (Kotlin: `JSESSIONID`), `HttpOnly`, `SameSite=Lax`, and `Secure` when `HINT_APPLICATION_URL` is https. It holds a `secrets.token_urlsafe(32)`, and the table only its SHA-256. A login always makes a new id. (b) **How long a session lasts.** A login: a cookie that stays when the browser closes, 7 days after the last use and 30 days at most, and for single sign-on no longer than the Auth0 token (h2). A guest: a cookie the browser forgets when it closes, 24 hours after the last use. Kotlin: in server memory, so until the server restarted or the session timed out (120 minutes idle, `server.servlet.session.timeout`), and the cookie was forgotten when the browser closed. `expires_at` moves at most every 5 minutes. Users who are logged in to Kotlin when this goes live must log in again. (c) **A new visitor is the guest user, with no session row**, until something needs one: `POST /guest/version`. Kotlin made a session for each visitor. (d) **Auth0.** The flow is Kotlin's (the same `/authorize` parameters and `/v2/logout`), with authlib's `AsyncOAuth2Client` instead of pac4j, and with PKCE added (`code_challenge` on `/authorize`, `code_verifier` on `/oauth/token`). The `state` is authlib's random token (Kotlin: base64 of a UUID). It and the code verifier are kept in a cookie of their own (`__Host-hint_login` on https, `hint_login` on http; `HttpOnly`, `SameSite=Lax`, 15 minutes), not in the session (Kotlin: the session), so the start of a login writes nothing. Only the latest start can finish. Errors: no state 400 and the wrong state 400, with Kotlin's messages; Auth0 failing (no token, no user) is an unexpected error (500); no email or not an email is `invalidEmail` (400), all as in Kotlin. A callback with the right state and no code (the user said no at Auth0) is 400 `auth0CodeMissing` (Kotlin sent the browser to `/` without a login). Kotlin's quirk 'the redirect_uri sent to the token endpoint has the client name twice' is gone. (e) **An existing user is found whatever the case of the email, and their id is used.** Kotlin used Auth0's spelling as the session's user, so a user whose email Auth0 spells in another case could not make projects (quirk `sso/test_sso_login_with_different_case_email_matches_user_but_keeps_idp_case`). (f) **The login page** is a static file, `app/pages/login.html`, with no template engine. Its script asks `GET /login/options` what to show, and puts the message of an ended session (`?error=SessionExpired&message=...`) in as text, never as HTML (Kotlin's page put the `username` of the query string in the page as it was, quirk `test_login_page_does_not_escape_username`; the username field is gone with the password form). **`redirectTo` is gone**: Kotlin kept it from `GET /login?redirectTo=` and went there after the login, but nothing has sent it since Data Exploration was removed. A login always goes to `/`. Like Kotlin's, the page is in English only. (g) **Logout** deletes the row. A user who logged in with Auth0 goes to Auth0's logout (as in Kotlin), anyone else to `/login`. (g2) **Settings**, for the deployment: `HINT_APPLICATION_URL` (Kotlin `application_url`), `HINT_AUTH0_DOMAIN` (`oauth2_client_url`), `HINT_AUTH0_CLIENT_ID` (`oauth2_client_id`), `HINT_AUTH0_CLIENT_SECRET` (`oauth2_client_secret`), `HINT_AUTH0_AUDIENCE` (`oauth2_client_audience`), `HINT_AUTH0_SCOPE` (`oauth2_client_scope`, with spaces rather than `+`), and, new, `HINT_SESSION_ENCRYPTION_KEYS` (a secret, needed with Auth0). `oauth2_login_method` has no equivalent: Auth0 is on when its domain is set. (h) **Who the user is** comes only from the cookie: the old `X-Hint-*` headers are ignored. The Auth0 access token is in the row, encrypted with Fernet (`app/services/token_encryption.py`, key from `HINT_SESSION_ENCRYPTION_KEYS`), never in the cookie or an answer. Kotlin kept it in server memory. (h2) **The token's expiry ends the session.** Auth0's `expires_in` is kept (`access_token_expires_at`, 24 hours in the tenant), and the session ends then, even if it is in use: the user is a guest, endpoints that need a login answer 401, and the Vue app sends them to the login page. A token that no key decrypts ends the session too. Kotlin kept the session (up to 120 minutes idle) and kept using the token after it expired, and ADR refused it. (i) The access log masks any part of a path with an `@` in it (`GET /user/<email>/exists`). The traces still have the path. (j) **The contract tests** keep the goldens recorded from Kotlin, unchanged: they are the baseline. On a replay, the harness drops the golden's login steps (Kotlin's `POST /callback/formClient`) and logs in with `POST /dev-login` without recording it, so the steps after it are compared as before. The `auth/`, `sso/` and SSO-mode scenarios, and the identity bridge test, are about Kotlin's login (pac4j) and are skipped on a replay: the Python tests (`tests/api/test_login.py`, `test_web_sessions.py`, `test_users.py`) replace them. (k) **A guest's version is always version 1**, as in Kotlin (`getNextVersionNumber(null)` matched no row). Python had counted every version with no project, so a guest's version came after every other guest's; the contract test `test_two_guest_tabs_get_two_versions` found it once `POST /guest/version` moved here. (l) **Until Kotlin is unrouted (D23)**, the paths nginx still sends to Kotlin have no login, as Kotlin no longer has the session: a logged in user is a guest there (401 on its secured paths). The Vue app calls none of them; the contract tests do (`/adr/output`, `/adr/vmmc`, `/adr/key`, the trailing slash variants such as `/adr/datasets/{id}/`, `/user/%2e%2e/exists`).

## Deferred until Kotlin is gone

Changes that need the database to change. Kotlin shares the database, so they wait until Kotlin no longer runs against it.

- **Z1. One file per type for a version, enforced by the database.** The primary key of `version_file` is `(version, hash, type)`, so nothing stops a version having two rows of one type with different hashes. Today the code keeps to one row per type (D9 (e)). Two uploads at once of a type the version has no file for yet can both insert: with the same file the second fails on the primary key (a 500), and with different files the version gets two rows of that type, and `GET /session/files` shows one of them. Kotlin has the same race, and a lock would only order Python against Python, so Python does not take one. To fix it: (1) find and remove duplicate `(version, type)` rows that exist already (the migration fails if there are any), (2) add `UNIQUE (version, type)`, (3) replace the select and update or insert in `VersionRepository.save_version_file` with one `insert ... on conflict (version, type) do update`, and (4) add a test with concurrent uploads to a version with no file (it needs Postgres, as SQLite does not run the requests at the same time). `set_files_for_version` (delete all, then insert) can use the same constraint.
- **Z2. Drop what password login used.** The `ADR_key` and `onetime_token` tables (D11). Check first that nothing in production uses them.
